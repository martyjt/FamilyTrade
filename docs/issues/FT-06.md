## Scope

- Implement versioned typed rule definitions and bounded condition groups using the reviewed V1 rule-builder contract. Allow combinations of supported indicators/conditions for entry and exit; breakout/crossover are examples, not the only strategies.
- Support the user-approved indicator/operator catalogue and explicit typed comparisons/groups, long/short/both direction, validated periods, session/time filters and the reviewed exit/sizing/risk controls. Overnight positions must be representable; session filters must not implicitly force liquidation.
- Expose draft, validate, save-version and list/get operations for future UI and MCP callers.
- Make validation strict: reject unknown fields/types, unsupported constructs, non-finite values and excessive parameter bounds; execute no submitted code.

## Acceptance criteria

- [ ] Two strategy variants can be saved and run by changing configuration only.
- [ ] Edits produce immutable new versions; existing runs remain pinned to their original definition and content hash.
- [ ] Rule-node/type/group-depth, risk, time and indicator validation returns actionable errors; arbitrary expressions or code are rejected.
- [ ] Ownership is checked for drafts and every version read/write.

## Validation

Definition round-trip, invalid-input, immutable-version and cross-user tests using example strategies reviewed in FT-02.

## Exclusions

Visual workflow graphs, arbitrary Python, unrestricted rule languages, optimisation and strategy-performance claims.

## Feature catalogue planning clarification

The builder should expose one composable catalogue: price/volume inputs; mathematical
indicators; market structure/regime; and support/resistance features. Keep these as
small pure internal modules where useful, with one typed UI/MCP vocabulary.

Proposed initial examples: OHLCV and relative volume; SMA/EMA/RSI/ATR; explicitly
labelled bar-derived session VWAP; confirmed swing highs/lows and bullish/bearish/
sideways/unknown regimes; prior-session and rolling-window highs/lows as levels.
This is a proposed catalogue, not approval of exact formulas or every listed primitive.
FT-02 must settle definitions, lookbacks, warm-up, session resets, confirmation time,
level-cross/touch tolerance, availability time and complexity bounds before coding.

No lookahead: a pivot requiring later bars becomes usable only on confirmation,
never retrospectively at the pivot bar. Record feature values and rule reasons at
decision time, with versioned definitions. Test long/short, warm-up, equality and
confirmation boundaries. One-minute OHLCV supplies bar volume; exact volume-at-price,
aggressor delta and order-book features require additional source data and are deferred.

## Accepted configurability clarification — 2026-09-12

The user accepted configurable trading behaviour through shared UI/MCP strategy
versions. Presets do not permanently fix trade direction, entry lifetime or filter
choices. FT-02 (#3) carries the full clarification and its two independent review
results. It supersedes fixed-sounding preset language in the earlier strategy draft;
the original source packet/review remains unchanged for provenance.

Setup expiry and entry-order lifetime are separate bounded configurable fields. The
one-bar entry lifetime is a proposed preset value, not a permanent engine constant.
Keep temporal causality, effect deduplication, ownership and higher-level caps
enforced. New algorithms/order models may need reviewed capability extensions.

This acceptance settles product direction, not every numerical default. Coding
readiness is unchanged. Next FT-02 work is the paper order/fill and risk contract,
including configurable activation/TTL, costs, ambiguous candles and overnight cases.
