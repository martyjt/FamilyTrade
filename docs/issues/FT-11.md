## Problem

Strategies need to run continuously on newly completed bars with isolated state and clear behaviour after outages.

## Dependencies

- https://github.com/martyjt/FamilyTrade/issues/8 — [FT-07] Build the deterministic decision and paper-fill engine
- https://github.com/martyjt/FamilyTrade/issues/10 — [FT-09] Integrate ongoing futures ingestion and scheduled gap repair
- https://github.com/martyjt/FamilyTrade/issues/11 — [FT-10] Persist backtest runs and execute them as owned background jobs

## Scope

- Implement explicit start/pause/stop operations pinned to user, account context, contract, strategy version and data mode.
- Persist lane state, consumed event identity, decisions and simulated fills at a tested transaction boundary.
- Warm indicators from the user's archive; handle restart and late corrections according to FT-02 rules.
- On stale feeds or unexpected gaps, pause new paper actions and show the reason. Mark any historical catch-up as reconstructed rather than contemporaneous forward evidence.

## Acceptance criteria

- [ ] Two simultaneous lanes share the user's incoming data but never share cash, orders, fills or risk counters.
- [ ] A process crash at decision/fill persistence boundaries produces no duplicate action on replay.
- [ ] Repeated bars and historical repairs cannot silently trigger duplicate or stale forward entries.
- [ ] Active lanes remain on their saved strategy version until explicitly changed and the change behaviour is documented.
- [ ] A second user's data, state and control operations remain inaccessible.

## Validation

Compare controlled forward replay with the backtest engine; force crashes around checkpoints and exercise stale feeds, duplicate events, pause/resume and independent lanes.

## Exclusions

Broker paper-account lane isolation, real orders, auto-roll execution and unattended LLM loops.

## Accepted paper controls and recovery — 2026-09-12

- Provide both distinct actions: **Pause new entries / keep managing exits**, and
  **Close positions and stop**. The second requests simulated liquidation under the
  reviewed fill model; it cannot report a position closed before an eligible fill.
- Persist operator intent separately from outage/deployment status. Manual pause or
  stop survives reconnect/redeploy and requires an explicit user action to reverse.
- Automatically resume previously running paper lanes only after repaired state,
  verified fresh eligible data and consistency checks. Stay paused with a visible
  reason when recovery fails. Respect sessions and overnight positions.
- Stale/offline feeds cannot produce fabricated current fills. A close-and-stop
  request can remain pending until executable; define handling of existing pending
  entries/exits and later user actions in the FT-02 transition table.
- Historical reconstruction is labelled separately from contemporaneous forward
  evidence. Repeated controls/recovery events cannot duplicate decisions or fills.

Acceptance includes each action with flat/open positions, stale feeds, closed
sessions, reconnects and redeployments. Verify UI and MCP share these operations,
and that a manual pause cannot be overridden by automatic recovery.

## Deployment handoff acceptance

- [ ] Worker replacement uses FT-08 fenced ownership and an atomic event/state/

  takeover preserve an overnight position and manual pause/close intent.
- [ ] Report measured processing gap and replay outcomes for FT-18 release evidence;
